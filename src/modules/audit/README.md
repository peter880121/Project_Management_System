# Audit

Audit trails are first-class records. Preserve actor, optional project scope, action, entity, before/after state, IP, user agent, and UTC timestamp. Never store PHI.

`recordAudit(tx, event)` requires a Prisma transaction client. Business services update the record and write its audit event in the same transaction, so an audit write failure rolls back the operation. MySQL triggers reject audit row updates and deletes, including attempts made outside Prisma. Events include task status changes and assignments, role changes, exports, AI suggestion decisions, and RAG retrieval provenance (`query`, `hitIds`, `durationMs`, `degraded`).

`GET /api/audit` and `POST /api/audit/summary` are restricted to ADMIN and QA. The project scoped compliance agent reads up to 100 matching audit events plus the project's task, requirement, and test traceability records; time and actor filters constrain the audit event window. It reports completed tasks linked to missing or non-passing tests and requirements updated after linked tasks. AI citations are checked against the input ID set. If the model is unavailable or returns invalid output, the UI receives deterministic findings and raw audit events. Every scan writes an `AI_AUDIT_SUMMARY_GENERATED` audit event with filters, source audit IDs, result mode, and finding count. The `projectId` column scopes logs directly and is indexed; migration backfills project ownership for known task, requirement, test, document, suggestion, and sync-failure records. User/permission events remain global. The query page is at `/audit`.

If an audit insert fails, the associated business transaction aborts. RAG callers must not return/use retrieved context if provenance cannot be persisted. The database stores the full retrieval query as required for traceability; upstream input handling must continue to reject real PHI.
